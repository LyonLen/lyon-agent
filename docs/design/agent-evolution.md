# Agent 演化机制设计（淘汰 / 考核 / Workflow 固化 / 三层记忆 / 推荐路由）

> 来源：2026-10-11 晚间需求批（12 条口述）。目标：让 lyon 从"大模型走一步决定一步"
> 演化为**有评分、有淘汰、有固化流程、有路由网络**的机械执行体系——模型只负责
> 它擅长的部分（填内容、做判断），流程、选拔、调度都由确定性机制承担。
>
> 每节末尾标注了与现有代码的接入点，全部可增量实现，不推翻现有架构。

## 1. A 淘汰机制（候选竞争 · 错因归纳 · 十轮考核）

### 1.1 候选 A（Agent Profile）

一个候选 = 可替换的执行配置，全部外置为数据文件（`~/.lyon/agents/<id>.json`）：

```json
{
  "id": "coder-fable-medium",
  "model": "claude-fable-5",
  "prompt_ref": "prompts/coder.md",        // 系统提示（workflow 也可挂这里）
  "tools": ["read_file", "edit_file", "run_shell", "grep"],
  "params": { "effort": "medium" },
  "parent": "coder-v3",                    // 变异来源，用于追溯
  "gen": 2                                 // 第几代
}
```

**关键点**：候选之间只允许差异在 {模型, 提示, 工具白名单, 参数}——同一套任务、
同一套评分器，保证比较公平（同卷同批）。

### 1.2 评分：多条件满足 → 取总分最高者上岗

评分器 `score(run, groundTruth) → Scorecard`，纯函数、可离线重放：

| 维度 | 权重（默认） | 说明 |
|---|---|---|
| 正确性 | 0.50 | 有标准答案：精确/包含/单元测试通过；无标准答案：裁判模型盲评 |
| 效率 | 0.20 | 步骤数 / token 相对基线的比值（steps 面板数据直接可用） |
| 成本 | 0.15 | 实际花费（usage 表已有计价） |
| 规范 | 0.15 | 是否走了要求的 workflow、是否有越权工具调用（hooks 审计） |

- 同一任务派发给 **K 个候选并行尝试**（run 子命令批量跑，mockapi 可离线）；
  每个条件维度先设**门槛线**（正确性 ≥ 0.8 之类），全部过门槛者中**总分最高**的
  拿到该类任务的在岗资格——"满足多个条件，选得分最高的 A 卷出来干活"。
- 结果写 `~/.lyon/leaderboard.json`（任务类 → 在岗 A + 各候选 Scorecard 历史）。

### 1.3 有正确答案时的失败归纳（自己总结错误条件）

失败不是直接淘汰，而是**一次定向修复机会**：

1. 失败 run 的完整轨迹（steps + 转录 + Scorecard）交给归纳器
   （低价位模型，固定提示）：输出 `{"failed_conditions":[…], "patch":"…"}`
   ——"错在没跑测试就提交"、"检索时漏了 config 目录"这类**可执行的条件**。
2. `patch` 落到候选的 prompt/workflow 上（追加约束段，带 gen 标记）→ **重试**；
   每个任务最多 `maxRetries=3` 代，每代必须比上代分数高，否则淘汰。
3. 归纳出的 failed_conditions 同时进④记忆的项目层——同类错误全场可见，
   不只是这个候选可见（一个 A 挂了，全体受益）。

### 1.4 每十轮一次考核（在岗者也要考试）

- **计数**：在岗 A 每完成 10 个生产轮次（hooks 的 prompt_end 计数，已有事件流），
  触发一次考核。
- **考核集**：`~/.lyon/exams/<任务类>/` 下的留出题（不与生产任务混用；有标准答案），
  3–5 题小批量。
- **规则**：考核分 ≥ 在岗门槛 → 继续上岗；连续 2 次不达标 → **重开竞争**
  （leaderboard 里候补候选自动获得挑战资格）。防止"上岗后漂移"。
- **反作弊**：考核题不进常规记忆检索（检索时按 exam 标记过滤），考的是真实能力。

### 1.5 接入点

- 新增 `pkg/eval/`：`Scorecard`、`score()`、`runExam()`；批量尝试复用
  `lyon run` 的无头执行（`cmd/lyon` 已有 run 子命令）。
- 候选与榜单是纯 JSON 文件 + 文件锁，无新服务。
- 全程走 `pkg/hooks` 审计（已有 EvPromptEnd/EvToolExec 事件），成本统计复用
  `pkg/models` 计价。
- 测试：`internal/mockapi` 造 K 个行为不同的 mock 模型即可离线断言淘汰逻辑。

## 2. 知识覆盖率测试（需求评审时"脑子里过了多少代码"）

**类比**：程序员做需求评审时，能当场说出涉及哪些模块、哪些数据流——说不全就是
没吃透。Agent 同样可以在动手前测一次"脑内库存"。

### 2.1 两阶段检查

1. **生成清单（checklist）**：任务描述 + 项目记忆索引 → 生成本任务需要的知识项
   （涉及文件、接口约定、构建命令、坑——多数可直接来自④记忆的项目层，题库天然
   随记忆增长而增长）。每项是可判定的问答（"X 函数的错误码语义是什么？"）。
2. **闭卷作答**：当前 A（或被测候选）**不带工具**回答全部条目——这就是
   "不翻代码，先说脑子里过了什么"。
3. **对答案**：与 checklist 标准答案比对 → `coverage = 命中 / 总数`。

### 2.2 用途（三处消费）

- **开工前门禁**：coverage < 阈值（默认 0.6）→ 先把缺口条目**定向注入**上下文
  （把对应记忆项召回进 system note，`PushSystemNote` 已有机制），或提示补检索；
  注入后复测，仍低则换更强候选（喂给①的选拔）。
- **Workflow 固化前资格**：提案固化的 A 必须先过该类任务的历史覆盖率考核
  （与③联动）。
- **记忆质量信号**：清单项在记忆里查不到 → 记为"知识缺口"，进④的补录队列
  （该记没记的，比记错的更先暴露）。

### 2.3 接入点

- `pkg/eval/coverage.go`：清单生成与判分各一次 LLM 调用（subagent 档模型）。
- 门禁挂在 workflow 执行器入口（③）与 `lyon run --exam` 开关后。
- 记忆检索复用 `pkg/memory`（缺口直接写 hooks 审计）。

## 3. Workflow 固化体系（自由发散 → 固定流程 → 机械执行）

### 3.1 生命周期

```
探索期（自由）                固化期（机械）
─────────────                ─────────────
plan/默认模式自由尝试  ──N 次成功+考核通过──►  序列化为 workflow 文件
（允许走一步看一步）      （用户也可手动 /flow save）
                                             │
同类新任务 ──分类命中──► 机械执行器逐步推进 ◄──┘
                        （LLM 只做节点内填空，不决定控制流）
```

- **Workflow 文件**：`~/.lyon/workflows/<slug>.json`——有序节点列表，每节点：
  `{name, tool, prompt_template, inputs, exit_criteria, fallback}`。控制流是
  数据不是代码：顺序、条件跳转（基于 exit_criteria 的判定结果）、并行组。
- **固化时机**：同一类任务连续成功 `N=3` 次（从 steps/审计中聚类同一 tool 序列），
  或用户显式 `/flow save`。固化前须过一次②覆盖率检查 + ①考核。
- **命中匹配**：任务分类器（关键词/嵌入粗排 + 便宜模型确认）对 workflow 的
  `trigger` 描述打分，>阈值即命中；**命中后不允许自由发挥**——"workflow 确认下来，
  就应该按固定流程走"。偏离只发生在节点内 LLM 填空的输出里。

### 3.2 机械执行器（不是 LLM 决定下一步）

`pkg/flow` 状态机：`tick(node)` → 按 node 定义组 prompt（模板插槽填任务内容）→
调模型**只要求产出该节点的结构化产物**（文件、测试结果、评审意见）→ 按
`exit_criteria` 判定（确定性检查：命令退出码、测试通过、产物存在；必要时裁判
模型只判这一小步）→ 进入下一节点。LLM 在节点内自由组织语言与实现，
**但"下一步做什么"永远由状态机决定**——这就是"真正机械的一套机制"。

### 3.3 软件开发标准 workflow（内置模板）

随库提供四条 builtin，开箱可用、可被检出到用户目录后修改：

| slug | 节点流 |
|---|---|
| `feature-dev` | 需求澄清 → 方案设计(plan 模式) → 实现 → 自测(跑测试) → 评审 → 交付 |
| `bugfix` | 复现 → 定位(二分/检索) → 最小修复 → 回归测试 → 总结 |
| `code-review` | 变更清单 → 逐文件审 → 按类别给结论 → 必要时自动改 |
| `release` | 状态检查 → 版本号 → changelog → 构建验证 → 打 tag |

### 3.4 接入点

- 新增 `pkg/flow`（状态机 + JSON schema）；执行器复用 Session 的工具与审批
  （每个节点工具调用照常过 default/bypass 审批语义）。
- 分类器先用关键词+`pkg/models` 元数据，嵌入检索二期再上。
- steps 面板天然显示 workflow 节点（节点即一条 step 分组，复用现有父子结构）。

## 4. 三层记忆（热 / 本地 / 远端，高效检索）

现有基础已就位：热/冷分层 + team/personal/project 作用域 + 云同步
（`pkg/memory`）。本节是把它补成设想中的**三层 + 高效检索**：

| 层 | 位置 | 内容 | 检索方式 |
|---|---|---|---|
| L1 热（常驻） | system prompt 注入 | hot 标记的站立偏好/硬约束（个位数条） | 无需检索，全量在场 |
| L2 本地冷 | `~/.lyon/memory/`（项目/个人） | 项目约定、坑、命令 | **倒排索引 + 二元组切词**，毫秒级本地查 |
| L3 远端 | 云端（现有 sync 通道） | 团队共享知识 | 按需拉取增量到 L2 缓存，查本地副本 |

- **检索性能与覆盖率**（对"希望比 grep 更快更全"）：构建时把每条 fact 切成
  词项+二元组写入 sidecar 索引（`memory.idx`，mmap 只读），查询走索引取候选 →
  小范围精排；比全量 grep 少扫文件，召回靠二元组补足词形变化。
  索引失效检测 = fact 文件 mtime/hash，重载是增量的。
- **方言/分层检索**（口述"检索方言"理解为分层路由）：查询先按作用域优先级
  （team → project → personal）与热度过滤，L3 未命中才回源远端。
- **与②联动**：覆盖率检查的缺口项回写 L2；蒸馏（已有 Distill）继续当"晋升通道"，
  考核归纳的 failed_conditions 也走这里。

## 5. 模型自知与推荐路由网络

### 5.1 自知（知道自己用的底层模型、知道自己不擅长什么）

- 模型身份与能力画像已在 system prompt / header（`pkg/models` 知识库：窗口、
  参数、知识截止）。补一张**能力维度表**进知识库：`{推理深度, 长程执行, 开放性
  任务, 速度, 成本}`（0–5，人工基线 + 考核实测校准）。
- 任务入口先做**开放性分级**（收敛性：有标准流程/答案 vs 开放性：设计、权衡、
  创作）。系统提示里教 A："当任务开放性高于你的画像得分，且存在画像更高的
  候选时，**推荐而不是硬上**"——推荐以结构化输出
  `{"recommend": "<agent-or-model>", "reason": …}`，走现有 `run_subagent` 分发。

### 5.2 推荐缓存 → 路由网络（总入口慢慢结网）

```
任务 ─► 分类(任务类 c) ─► 查路由表 R[c]
                            ├─ 有 ─► 直接派给 R[c].agent（历史得分最高者）
                            └─ 无 ─► 当前 A 尝试 + 按①评分
                                      └─ 结果写入 R[c]（分数、耗时、推荐记录）
```

- `R` = `~/.lyon/routing.json`：任务类 → 在岗 A + 置信度 + 样本数。
  **每次考核与生产评分都回写**——用得越多、考得越准，路由越准。
- **网络效应**：每类难题都沉淀出"该交给谁"；新任务先问网络，网络没有才现场
  选拔（选拔结果回网）。总入口（chat/run 的派发处）就是这张网的唯一查询点。
- 与①同一张 leaderboard 数据：路由选择 = 考核分的消费端，淘汰 = 生产分的
  更新端，闭环无新增存储。

### 5.3 接入点

- `pkg/routing`（分类 + 查表 + 回写，纯文件）；分类一期用关键词/规则，
  与③的 workflow 分类器共用。
- 推荐输出在 TUI 中以蓝色提示行展示（复用 steps 面板的 cBlue 语义）。

## 6. 实施顺序（增量，每步独立可验收）

| 期 | 内容 | 依赖 |
|---|---|---|
| 一期 | ①评分器+榜单+十轮考核（先做，一切数据的源头） | 无（run + hooks + mockapi 已够） |
| 一期 | ⑤能力画像 + 路由表雏形（读榜单选人） | ①的分数 |
| 二期 | ③workflow 提案/固化 + 机械执行器 + 4 条内置模板 | ①的"规范"维度 |
| 二期 | ②覆盖率门禁（接入 workflow 执行器） | ③、④ |
| 三期 | ④检索索引升级（倒排 sidecar） | 现有 memory |
| 三期 | ①的错因归纳回写 + ⑤网络化（跨任务类迁移） | 一、二期全部 |

**验证原则**：每期先在 `internal/mockapi` 离线跑通（可控的假模型 + 假答案），
再接真网关；所有评分/路由决策可离线重放（输入输出都是文件）。

## 7. 重定义（2026-10-23）

> 口述需求："进化的 agent 可以共识共享；专长知识、专长技能各有自己的空间，
> 自己进化；不同场景选择不同的 agent；评测集基于项目动态生成；流程固化不止
> 形成 skill，还要形成不调 AI 的自动化 workflow，可作为组合单元给 AI 调用。"

### 7.1 动态项目评测集（pkg/eval/project_exam.go）

种子题库（8 类）之上新增 `project` 类：题目**从项目本身生成**——go.mod（模块
路径、Go 版本）、README 首个标题、cmd/ 入口目录、项目记忆层（`pkg/memory`
project 作用域的 hot facts）——全部输入哈希成 `Exam.Fingerprint`。项目一变，
指纹变化，`exams/project.json` 自动重新生成（未变则沿用，手改保留）。答题者
仍然闭卷无工具，但携带项目的站立上下文（结构摘要 + 事实全文），考的是"上下文
管线是否新鲜、能否抽取"，不是查资料。考核时钟（§1.4）每个生产回合同时给
`project` 类记一格，十回合自动开考。接线点：`loadExam()` 四处
（kickExam / runContest / kickFlowSave / runExamCLI），`RunExam` 改为并发
逐题（index 保序）。

### 7.2 专长空间与共识共享（pkg/space）

每个 agent 在 `~/.lyon/agents/<id>/` 下拥有两个专属库：

- `knowledge/*.md` — 专长知识（frontmatter: name/description/owner/endorsed-by）
- `skills/<name>/SKILL.md` — 专长技能（与 `~/.claude/skills` 同格式，扫描器直接复用）

共识层在 `~/.lyon/commons/{knowledge,skills}/`。**背书计数**决定晋升：条目初始
只有 owner 一个来源；第二个**不同**来源——另一 agent 保存了相同 body（两 agent
收敛到同一事实，hash 比对互签），或一次竞选胜利（`contest:<class>`）——即达
共识，复制进 commons（复制不移动，专长空间保留原件）。commons 技能随 system
prompt 的 skills 段下发给所有会话；`space` 工具（list / save_knowledge /
save_skill / share）让模型管理自己的空间，写不进别人的。会话用
`Session.SetAgent/Agent` 携带身份（默认 "self"），路由换人时自动切换并注入
`space.Brief`（该 agent 的专长清单，PushSystemNote）。诊断错因
（rememberDiagnosisSpace）同时落进当前 agent 的空间。

### 7.3 自己进化（pkg/eval/evolve.go）

失败不再丢失：诊断归纳（§1.3 diagDone）或闭卷考试不及格（examDone）都会
`EvolveChild(parent, lesson)` 生成下一代候选——`<parent>-g<gen>`，继承
model/effort + **整份专长空间复制**（space.CopySpace）+ lesson 作为第一条
knowledge。`Gen/Parent` 字段复活。代际上限 3（链深与同胞数同限）；竞选里
每代必须比上代分数高，否则删档淘汰（runContest 内比对）。胜者自动
`ShareAll` 全空间进共识层（§7.2）。

### 7.4 场景路由收口（不同场景选择不同 agent）

§5 的消费端补全：`routingSwap` 换模型的同时，`adoptAgent` 把会话身份切到
胜出 agent（同一模型也切——一人格一空间），⇄ 提示行点名 agent。CLI 与 TUI
同一条接线。

### 7.5 流程固化 v2：脚本（pkg/flow/script.go）

固化不止 skill（文档，要 AI 逐条解读）——**绿过的命令序列直接冻结成脚本**：
`~/.lyon/flows/<slug>.json`（清单）+ `<slug>.sh`（人可直接跑）。`RunScript`
机械执行，**零模型调用**，`{{name}}` 参数占位、首错即停、绿跑回计 Runs 证据。
`flow` 工具（list/run/freeze）是给 AI 的组合单元：一次调用跑完整条序列，
或把刚跑绿的序列固化。skill 冻结后仍要 token；脚本冻结后不要。
