## 0. 一句话

对话进行中，把聊过的内容长成一张**实时思维导图**，住在独立 pane 里、**与 chat 平级**（#51 用户裁定：不要聊流内嵌卡片）；
**用户在图上做的调整会回流成一条事件推进 chat，并触发 agent 自动提问。**

后者决定了它的性质：这不是视图，是**第二条输入通道**。

---

## 1. 为什么不抄 todo_write 的模式

plan 卡的机制是 `todo_write` 工具 + 无状态渲染：模型每次发**完整列表**，事件
`tool_exec_start.inputJson` 带全量，web 端 `web/src/todos.ts:parseTodos` 直接解析上屏，
服务端零状态。它成立是因为两件事刚好凑齐——列表上限 20 条，且拆步骤本来就是行动的一部分。

思维导图两条都不成立：

| 障碍 | 具体后果 |
|---|---|
| 全量重写会长大的树 | token 随轮数**平方级**增长，30 轮就撑不住 |
| 「理解驱动」而非「行动驱动」 | 模型没有动机每轮重画一遍，靠自觉必然漏写、越走越旧 |

结论：**必须旁路生成**，不占主轮、不依赖模型自觉。

## 2. 数据流（全部挂在已有挂钩上，不新造轮子）

```
对话 turn ──► transcript（已有）
     └─► prompt_end tap（已有：pkg/server/store.go SetPromptEndObserver，
                          pkg/evolve 就是这么挂的，Hook 自带 goroutine 不堵 hub）
           └─► pkg/mindmap 蒸馏器（新；仅 mindmap 模式 — Image #71，
               其他模式的会话不画图）
                 ├ 输入：转录尾部 ~6-8k token + 现有 map 的节点清单（id + label）
                 ├ 便宜模型，强制 JSON
                 └ 输出：只回「改了什么」的 diff（非全量）
                       └─► EVENT_MINDMAP_UPDATE → hub → web 卡片
                             ├─► snapshot 持久化 → /resume 能重建
                             └─► TUI 缩进大纲（挂 cmd/lyon/steps.go，**不碰 tui.go 只减不增红线**）

用户在图上编辑 ──► EVENT_MINDMAP_EDIT（origin=user）→ hub → chat
                       ├─► 图上立刻生效（本地乐观更新，pinned）
                       └─► 合并窗口 800ms 后合成一条消息进 chat → 触发一轮 → agent 自动提问
```

## 3. 数据模型

```proto
// proto/lyon/v1/event.proto —— 事件类型新增（编号顺延）
enum EventType {
  // ...已有 1-16
  EVENT_TYPE_MINDMAP_UPDATE = 17;  // 结构变化（蒸馏器产出）
  EVENT_TYPE_MINDMAP_EDIT   = 18;  // 人的编辑动作（图 → chat 的输入通道）
}

// 节点载荷放 Event.attrs（已验证的 forward-compat sink：
// event.proto:90 `map<string,string> attrs`，pkg/agent Event.Attrs 同源），
// payload 为 JSON 字符串，proto 定型前不必churn字段号。
```

节点 JSON（`attrs["node"]` / `attrs["nodes"]`）：

```json
{
  "id": "b-storage",            // 稳定 id，蒸馏器必须复用已存在的 id
  "parent_id": "root",
  "label": "存储与持久化",       // 提炼短语（完整不截断 — Image #62；服务端仅 200 字上限兜底）
  "source_turn": 7,             // 该话题首次出现的 turn，用于「点节点跳回原话」
  "kind": "branch",             // branch | decision | fact | open_question
  "status": "active",           // active | parked
  "pinned": false,              // 人改过 → true，蒸馏器不得改/删/挪
  "edited_by_user": false,      // 与 pinned 同义冗余，供渲染弱化标记
  "tombstone": false            // 人删掉的一支：保留墓碑，作负信号
}
```

**为什么要有 tombstone**：删除是负信号。用户剪掉一支 = 这条不重要，蒸馏器不能再长回来。

## 4. 三条硬规则（非技术判断，须用户点头）

### 4.1 人工改动是权威

`pinned` 节点：蒸馏器只能在它**下面**新增子节点，**不能**改名、删除、改 parent、改 kind。
违反即丢弃该条 diff 并在 audit 记一笔 `mindmap.pinned_violation`。

### 4.2 图上操作 ≠ 执行授权

`EVENT_MINDMAP_EDIT` 只能产出**一条对话消息**，永远不能直接触发工具执行。
写文件 / 跑命令 / 改配置仍然走审批链（`lyond` path-aware approval、per-seat ledger）。
注释写明：这是安全边界，不是实现细节。

### 4.3 图是「待你确认的理解」，不是「结论」

**设计基线（2026-11-03 用户拍板）。** 这条是 M1 就要有的，不等 M2。

模型蒸馏出来的节点，天生是**二手阅读**：它会把限定条件、你的犹豫、前后矛盾压平成一句短语，
而图形天生比文字更像结论——**一张失真的图比没有图更危险**，因为人会拿它当依据。

所以视觉上必须区分两种态：

| 态 | 视觉 | 语义 |
|---|---|---|
| `proposed`（模型猜的） | 虚线 + 灰字 | 待你确认，可疑是它的本分 |
| `confirmed`（你认定的） | 实线 + 正常字重 | 你点过确认，或你亲手编辑过（`pinned`） |

节点上的确认是**一键**动作，不打断对话。`proposed` 节点超过 N 轮未确认不自动升格——
只会被新的蒸馏结果替换或剪掉。

推论：这张图的正确读法是「**这是 lyon 目前对你说的话的理解，有错请你改**」，
而不是「这是这次讨论的结论」。卡片标题就按前者写。

### 4.4 自动提问的提示纪律

（触发条件：**仅 `origin=user` 的编辑**且会话处于 `mindmap` 模式且 `LYON_MINDMAP_ASK`
未关 —— 双闸见 §8；其他模式下编辑只落本地 notice，不产生消息。agent 自己的
`map_ops` 落图是对选区提问的**答复**，只计入 A5 批次，绝不触发自动追问
—— 不然 agent 会对自己刚写的改动提问。）

agent 收到这条消息时：

1. 先**一句话复述**它理解的改动（让人能立刻纠正误读）；
2. 只问**一个**最关键的问题；
3. **不擅自动手**——不写文件、不改代码、不开始执行。

## 5. 并发与 revision（乐观锁，人工优先）

蒸馏是一次外部 LLM 调用，期间用户可能正在改图。规则：

- 每次蒸馏携带出发时的 `revision N`；
- 提交时若当前 revision ≠ N 且期间有**人工**改动 → **丢弃本次蒸馏结果**（人工优先），下一轮自然重算；
- 若期间只有模型侧变化 → 顺序应用即可。

失败降级：蒸馏超时/JSON 坏 → 静默跳过本轮，图上不出现半个节点，audit 记一笔。

## 6. 蒸馏器提示约束（防噪声、防漂移）

- **帽子**：深度 ≤ 4、节点总数 ≤ 60、单支子节点 ≤ 8；
- **准入**：只写「有结论 / 有决策 / 有事实 / 有悬念」的内容，寒暄与过程丢弃；
  **且主语必须是讨论的主题本身**（产品/项目/领域）——凡讲「这张图怎么组织」的
  内容（重摆层级、层壳去留、节点搬到哪、删哪条留哪条、编辑操作与理由、
  蒸馏/自动提问机制）即使句式像结论也**不入图**；入错的旧元节点当轮 park
  （Image #58/#59 —— 元讨论反复被蒸成节点）；产品自身的架构悬念（队列接哪层）
  是真内容，保留。转录侧同步过滤：web 合成的「图编辑通知」整条剔除（仅保留
  turn 槽位对齐跳转锚点）、`[导图选区…]` 标记与 `【系统 ·】` 后缀剥掉；
- **剪枝优先于扩张**：图反映**当前理解**，不是越长越全；被新信息推翻的分支置 `parked` 而非保留；
- **id 复用强制**：输出必须引用已有 id；新节点用 slug（`b-<ascii>`），服务端按 label 相似度兜底合并，避免每轮换一种组织方式导致整图闪红；
- **不代拟**：没有依据的结论不写进节点（对齐「缺指标时如实留白」原则）。

### 7.3 圈选与批量提问（2026-11-03 用户补充）

选中多个节点，一句话要求编辑或询问；chat 的答复再作用回图。

**选区模型**：`selection = {node_ids: string[], ts}`，跨分支允许，前端持有，
事件里带**快照**（节点可能在你提问期间被蒸馏改动）。

**手势**（对齐 Windows 肌肉记忆）：

| 手势 | 行为 |
|---|---|
| 空白处拖拽 | 拉出圈选框，替换选区 |
| `Shift` + 拖拽 | 加选 |
| `Ctrl`/`⌘` + 点击 | 单节点切换选中 |
| `Esc` / 点空白 | 清空 |
| 双击节点 | 进入单节点编辑（重命名 / 注解） |
| 按住滚轮拖拽 | 平移画布（任意位置起手，含节点上；不触发圈选） |
| `Ctrl` + 滚轮 | 以光标为锚缩放（双击空白复位到自适应） |

**选区浮条**（**停靠在图顶部的布局行** — 占画布上方空间、画布让位重算缩放，
**不遮挡任何节点**，Image #55 否决了悬浮锚定方案；不占对话流）：
`已选 3 个节点` + 预设动词 + 自由输入框。
预设动词把自然语言的不确定性压下来：`合并` `归类到…` `改写` `它们矛盾吗` `解释`。

**分流：这是快不快的分水岭**

| 操作 | 走哪条路 | 延迟 | token |
|---|---|---|---|
| 结构：合并 / 改 parent / 删除 / 排序 / park | **本地确定性**，零 LLM | 立即 | 0 |
| 语义：改措辞 / 判断矛盾 / 生成新分支 / 解释 | 走 chat 一轮 | 1–3s | 计入 §8 |

把结构操作也发一轮 chat 是常见的设计错误：你会等 3 秒、烧一次钱、还可能被模型改歪，
而这件事本地 0ms 就能做对。**结构走手，语义走嘴。**

**答复怎么作用回图**

- 语义类请求，agent 必须回**结构化 `map_ops`**（`merge / set_parent / rewrite / add / park / delete` + 目标 id），
  **不允许只回散文**——散文落不成图，「作用回图」就是空话；
- `map_ops` 落地时一律以 `proposed` 态写入 + 虚线高亮 diff，配一次「全部确认」；
  **绝不静默改 `confirmed` 节点**（与 §4.3 一致：你确认过的，只有你能改）；
- 选区信息随消息走：`[导图选区 3 个节点|id1,id2] <你的问题>` —— **id 直接嵌在标记文本里**
  （无 protoc/buf，不能给事件加 `attrs.node_ids` 字段；文本即线格式）。
  构造与剥除共用 `web/src/selask.ts`：**浮条与主输入框走同一条线**——输入框里
  直接发送，只要图上有选区就自动包标记（Image #64 「选中提问无效」：此前主输入
  裸发，模型根本看不到选区）。
  chat 渲染时把标记剥掉、按快照把 id 换成**可点的 label chips**——点 chip 回图上高亮该选区
  （选中环）；`【系统 · 选区提问纪律】`后缀**不进 feed**（Image #65 —— 系统提示
  直接怼在消息尾部读着像噪声；它只随线格式发给模型：改图只认一个
  ```map_ops 围栏，散文不落图）。队列行同样只显示人写的那行。

**防循环**：一次选区提问最多产出一批 `map_ops`；连续 3 批 `proposed` 未确认时，
浮条提示「先处理这 3 批未确认改动」——**提示本身可点击**：点它即圈出全部未确认的
提案节点（选中环），让「处理哪儿」有具体落点（Image #63），再配「全部确认」一键清账，
否则图上会堆屎。

**手性提示**：选中 N 个节点时，输入框顶部明确写「对 N 个节点提问 —
输入框直接发送即带选区（浮条：改写 / 矛盾吗 / 解释）」，
避免你以为在跟主对话说话、实际进了选区通道。

## 8. 开关与成本

| 开关 | 默认 | 作用 |
|---|---|---|
| `LYON_MINDMAP` | `on` | 总开关，`off` 后无蒸馏、无卡片、无事件 |
| `LYON_MINDMAP_ASK` | `on` | 图上编辑自动提问的**总闸**；`off` = 所有模式都只入 chat 不发轮 |
| 会话模式 `mindmap` | 按会话 | **画图与自动提问的分闸**（Image #61/#71）：只有 mindmap 模式蒸馏 —— 其他模式的会话不长节点、pane 不自动打开（读侧不变：已有图照常渲染，`/mindmap` 手动开，选区手动提问全模式可用）；且仅 mindmap 模式下图编辑才发轮，其他模式落一条本地 notice（「mindmap 模式外 — 未发轮」）；执行/审批与 default 完全相同。web 下拉第 4 项 + `/mode mindmap`（TUI shift+tab 不循环它；TUI 里该模式管蒸馏/大纲生长，无图编辑通道）；选中即自动打开图 pane |
| 蒸馏模型 | ⚠ 待确认 | 建议低价位模型（对齐 `docs/design/agent-evolution.md §1.3` 归纳器口径） |
| 成本量级 | 每轮 1 次调用，输入 6-8k，输出 ≤ 1.5k | 长会话下按轮计，非按 token 累积 |

合并窗口：编辑静默 800ms 后合成一条消息；窗口内多次编辑合并（改 A 又改 B → 一句话说清）。

## 10. 图 → memory 抽象（复用现有 memory，不新建存储）

### 10.0 复用哪套

`pkg/memory` 已经齐了，图只是它的**写入来源之一**：

| 现有能力 | 出处 | 图怎么用 |
|---|---|---|
| 三 scope：`team`(全局) / `personal` / `project` | `pkg/memory/fact.go:39-41` | 章节按 §10.3 判定表落 scope |
| 一 fact 一文件、name 即文件名、按 name upsert | `fact.go` 文件头注释 | 章节名稳定 → 重复抽取＝更新而非新增 |
| BM25 + CJK bigram 检索 | `fact.go` 包注释 | 中文章节名可被检索到 |
| hot tier 注入 | `pkg/tools/memory.go:42-55` | **只用一条索引，见 §10.4** |

不新增存储、不新增索引、不新增 scope。

### 10.1 硬纪律：只抽 `confirmed`

| 不抽什么 | 为什么 |
|---|---|
| `proposed` 节点 | 是模型猜的。入库＝把猜测沉淀成事实，与「缺指标时如实留白，不代拟不美化」直接冲突 |
| `open_question` 节点 | memory 是**结论库**，不是待办库；未决留在图上，图看得见它 |
| `parked` 分支 | 已被推翻的理解不该沉淀 |
| `tombstone` 分支 | 但抽取时必须**读**它：同分支不得复活 |

这一条是整节的命门。**虚线的还没确认，凭什么入库。**

### 10.2 分章节：一章一条 fact（用户问的「太大怎么办」）

- **一级分支 = 一章 = 一条 Fact**。本样本图 8 支 → ≤8 条 fact，而不是 36 条。
- 理由两条：① 36 条近似小 fact 会把 BM25 检索稀释掉（每次 `read_memory` 返回一堆碎片）；② 一条塞 60 节点的巨无霸 fact 检索同样不准。
- **单章正文超过 2KB** → 拆两级：`章节摘要` 进 memory，`明细` 留在图里 + 落 `docs/` 存档，摘要末行给路径链接。
- **章内二级切分**：若一章里某个 scope 的节点数 ≥2，允许再切一条（上限 +1）。例：本图「需求」章里既有项目事实也有你的口味要求。
- **命名稳定**：`导图-<主题slug>-<章节slug>`，例 `导图-对话实时思维导图-风险`。
  name 即文件名，**同一主题再抽一次是更新，不是新增**（幂等，用例 M5 钉住）。
- 正文格式沿用现有 frontmatter（`name / description / scope / tags / hot / created / updated`），
  `tags` 必带 `mindmap` 与主题 slug，便于整主题批量检索与删除。

### 10.3 scope 判定表（不允许模型自由心证）

| 内容特征 | scope | 例（取自本样本图） |
|---|---|---|
| 用户本人的偏好 / 口味 / 验收标准 | `personal` | 「图是待你确认的理解，不该显得权威」；「PPT 四条硬要求」 |
| 本仓库的事实 / 架构 / 红线 / 踩过的坑 | `project` | 「卡片挂 `prompt_end` tap，内核零复杂度增长」 |
| 跨项目的组织口径 / 人名 / 流程 | `team`（全局） | 「会议转写 speaker 标签不可信」；三箭人名对照 |
| 判不出来 | `project` | 最保守，不污染他人；正文首行标 `scope: 待定` |

强信号（`pkg/mindmap` 蒸馏器输出 `scope_hint`，服务端校验后落库）：
出现文件路径 / 包名 / 函数名 → `project`；出现「我 / 我的 / 我要」→ `personal`；
出现公司 / 团队 / 人名 / 跨项目流程 → `team`。

### 10.4 热层：只放一条索引——而且现在就已经超预算了

核实过的事实（这决定了图**绝对不能** `hot`）：

- 预算常量 `memoryHotBytes = 4096`（`pkg/tools/memory.go:21`）；
- 溢出行为是**整条丢弃，不是截断**：`store.go:424` `if used+len(entry) > maxBytes && any { return }`；
- 现状：项目热层 **4 条 / 8226 字节 > 4096**，单是 `26-27年汇报-sdas-skill-与软件团队定位口径.md`
  一条就有 **4722 字节**——一条就吃掉了整个预算。

所以：

1. 图**永不** `hot: true`（用例 M4 钉住：抽完记忆后 `HotText(4096)` 长度不增）；
2. 若确实需要「一眼看见有这张图」，只写一条 `导图索引-<主题>`，正文 ≤200 字节：标题 + 章节名逗号串 + 图文件路径；
3. **顺手登记一条独立欠账**：热层已超预算，至少 1 条 hot fact 每次会话都没进上下文，该清理或改双限（条数+字节）。不进本方案范围。

### 10.5 抽取时机：手动优先，自动只「提议」

| 触发 | 行为 |
|---|---|
| 图上「存成记忆」按钮 / web `/remember`（已存在） | 直接抽，走 §10.1–10.3 |
| 会话结束 | 若 `confirmed` 的 `decision|fact` 节点 ≥4 且本主题未抽过 → 卡片上出一次「抽成记忆？」提示，**点击才写** |
| 每轮蒸馏后 | **什么都不做**。禁止自动写 |

理由：memory 是长期资产，写入要过人的判断；每轮自动写＝图抖一下，记忆库就脏一点。

### 10.6 反向复用：图的第一批节点来自 memory

落地 §9 亮点 A（图当会话交接物）的反向一半：

- 新会话首条 prompt → BM25 检索 → 命中 fact 画成节点：`state=confirmed`（人写过的，不需要再确认）、
  `kind=fact`、`label` = fact 的 `description`、`source_turn=0`、`origin=memory`；
- 于是图**开场就有底子**，memory 也有了可见出口——它不再只是藏在上下文里的字符串。

## 11. 测试用例（按项目目标拆解，可直接落成 `*_test.go` 与 web 用例）

### 11.0 目标 → 子目标 → 用例

| 目标 | 可判定的子目标 | 用例 |
|---|---|---|
| ① 图要准，且不闪 | 结构合法、不代拟、id 稳定、该剪就剪 | G1–G4 |
| ② 你的改动说了算 | pinned 不可覆盖、删除不复活、并发不打架 | P1–P2、R1 |
| ③ 改动回流且不越权 | 防抖、提问纪律、零工具执行、散文不落图 | A1–A5 |
| ④ 能沉淀且不脏库 | 只抽 confirmed、一章一条、scope 正确、热层不爆、幂等 | M1–M5 |
| ⑤ 关掉无痕、坏了不崩 | 开关、降级、会话重建 | D1–D2、S1 |
| ⑥ 好看好用、改得快 | 跳回原话、TUI 大纲、提案态视觉、圈选与批量提问 | U1–U5 |
| ⑦ 成本可控 | 每轮上限、不随会话膨胀 | C1 |

### 11.1 蒸馏正确性（G）

| 编号 | 输入 | 期望 / 判据 |
|---|---|---|
| **G1** | 固定转录 fixture（≥12 轮） | 输出节点全部合法：`parent_id` 存在、无环、`depth ≤4`、`总数 ≤60`、`label 完整不截断`（仅 >200 字兜底裁切）、`kind ∈ {branch,decision,fact,open_question}` |
| **G2** | 同一 fixture + 一条**转录里并不存在**的结论注入断言 | 该结论**不得**成为 `decision` 节点（不代拟；断言按 label 相似度匹配不上） |
| **G3** | 连续两轮蒸馏，转录只追加内容 | 未变化分支的 `id` 完全不变，diff 只含新增节点（防整图闪红） |
| **G4** | 第二轮出现推翻第一轮某分支的新信息 | 旧节点转 `parked`，**不删除**；`kind/status` 变化随 diff 下发 |

### 11.2 人工改动权威性（P / R）

| 编号 | 输入 | 期望 / 判据 |
|---|---|---|
| **P1** | 人工把节点改名 → 下一轮蒸馏器返回「改回原名」的 diff | diff 被丢弃，节点保持人名；audit 记 `mindmap.pinned_violation` |
| **P2** | 人工删除一支（tombstone）→ 之后连续 3 轮蒸馏 | 同 label 节点不再出现 |
| **R1** | 蒸馏携带 `revision N` 在飞，期间人工编辑产生 `N+1` | 蒸馏结果**整批丢弃**，图中无该批节点（人工优先） |

### 11.3 回流与自动提问（A）

| 编号 | 输入 | 期望 / 判据 |
|---|---|---|
| **A1** | 800ms 窗口内连续 3 次编辑（改 A、改 B、删 C） | chat 只出现 **1** 条 `mindmap_edit` 消息，且三个改动都在其中 |
| **A2** | 收到 `mindmap_edit` 的那一轮 | 响应含一句复述 + `?`/`？` 计数 ≤1；该轮 `tool_exec_start` 计数 **= 0**（不擅自动手） |
| **A3** | 任意 `mindmap_edit` 事件 | 事件结构里**没有**可执行意图字段（无 `tool_name`/`input`）；即便文案里写了「帮我改代码」也不触发工具 |

### 11.4 沉淀（M）

| 编号 | 输入 | 期望 / 判据 |
|---|---|---|
| **M1** | 图里 6 个 `confirmed` + 4 个 `proposed` | `store` 仅新增与 confirmed 对应的 fact；proposed 一条都不落库 |
| **M2** | 8 支的样本图 | fact 数 ≤8（+章内二级切分 ≤ 每章 1 条）；name 形如 `导图-<主题>-<章节>` |
| **M3** | 三组样例（口味 / 仓库事实 / 组织口径） | 分别落 `personal` / `project` / `team` |
| **M4** | 抽取前后调用 `HotText(4096)` | 长度**不增加**（图永不 hot；只有索引条 ≤200 字节时例外，且需显式开启） |
| **M5** | 同一张图连续抽两次 | fact 总数不变（upsert 幂等），`updated` 时间戳推进 |

### 11.5 降级与重建（D / S）

| 编号 | 输入 | 期望 / 判据 |
|---|---|---|
| **D1** | 蒸馏超时 / 返回坏 JSON | 本轮静默跳过：图中无半截节点、revision 不推进，audit 有一笔记录 |
| **D2** | `LYON_MINDMAP=off` | 无事件、无卡片、**零 LLM 调用**（mockapi 断言未收到请求） |
| **S1** | 图长完后 `/resume` | 图完整重建，节点属性（`pinned`/`state`/`tombstone`）不丢，revision 连续 |

### 11.6 渲染与观感（U）

| 编号 | 输入 | 期望 / 判据 |
|---|---|---|
| **U1** | 点任意带 `source_turn` 的节点 | 跳到该 turn 的首条消息；TUI 大纲行数 = 节点数（剔除 tombstone） |
| **U2** | 样本图渲染 | `proposed` 虚线 / `confirmed` 实线，二者肉眼可分；以 `docs/design/mindmap-sample.png` 为视觉基线 |
| **U3** | 空白拖拽 / `Shift`拖 / `Ctrl`点击 / `Esc` | 分别得到：替换选区、加选、切换单节点、清空；选区跨分支可用 |
| **U4** | 圈选三支 →「合并」 | **零 LLM 调用**（mockapi 断言未收到请求），本地立即完成，无 chat 消息 |
| **U5** | 圈选三支 →「把措辞统一成 X」 | 产出 `map_ops` 并以 `proposed` 虚线落图，`confirmed` 节点不被改动；一次「全部确认」后转实线 |

### 11.6.1 选区话题的补充用例（A）

| 编号 | 输入 | 期望 / 判据 |
|---|---|---|
| **A4** | agent 对选区提问只回了散文（无 `map_ops`） | 图**不变**；chat 提示「需要结构化 map_ops 才能落图」，不得猜测意图擅自改 |
| **A5** | 连续 3 批 `proposed` 未确认，再发第 4 次选区提问 | 浮条先提示处理未确认改动（防堆屎），不静默继续叠加；提示可点击 —— 点击圈出全部未确认提案节点（Image #63） |

| 编号 | 输入 | 期望 / 判据 |
|---|---|---|
| **C1** | 20 轮会话 | 蒸馏调用 ≤20 次；单次输入 token ≤8k、输出 ≤1.5k（对齐 §8） |

### 11.8 黄金样本

- **结构与视觉基线**：`docs/design/mindmap-sample.js`（本场讨论的蒸馏结果）+ `docs/design/mindmap-sample.png`。
  它不是"正确答案"，是**当前理解的可对照快照**——实现跑出来像不像它，一眼能判。
- **转录 fixture**：需从真实会话导出（`$LYON_HOME/sessions/<hash16>.json`），
  **我不代造转录**——照「不代拟」原则，样本输入必须是真发生过的对话。
