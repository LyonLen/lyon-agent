lyon-agent user manual

1 ·Quick start

Two build commands, one line of credentials, three ways to run depending on the scene.

Build

# repository root (Go ≥ 1.25, no other dependencies)
go build -o bin/lyon   ./cmd/lyon     # terminal main program: CLI + fullscreen TUI
go build -o bin/lyond  ./cmd/lyond    # optional: OpenAI-compatible gateway / SSE service

Credentials (pick one)

# A · Anthropic official endpoint
$ export ANTHROPIC_AUTH_TOKEN=sk-ant-...

# B · OpenAI-compatible endpoint (the same key works, keep the /v1)
$ export ANTHROPIC_BASE_URL=https://token-plan-cn.xiaomimimo.com/v1
$ export ANTHROPIC_AUTH_TOKEN=<your-key>

Three ways to run

CommandShapeWhen to use
lyon run "task" one-shot runs to completion in scripts/pipes, -stats prints the usage report; approvals auto-deny when stdin is closed (fail closed)
lyon chat fullscreen TUI the daily driver: streaming transcript + side step panel + approval overlay; auto-saves on exit
lyon chat -c resume pick up last session after a restart (transcript replay, usage stats continued, steps panel restored as-is) 
$ ./bin/lyon chat                # enter the TUI; the first prompt injects local memory
$ ./bin/lyon chat -c            # continue the same session in another terminal window
$ ./bin/lyon tools              # list all tools (run_shell/read_file/…)
Storage root: all state (sessions, leaderboard, exams, workflows) lives in $LYON_HOME, default ~/.lyon. Change it before launch to isolate — tests, containers and CI rely on it to stay off the real home.

2 ·UI tour

The fullscreen workspace of lyon chat splits into four areas, each with one job. The UI defaults to English; /lang zh or LYON_LANG=zh before launch switches to Chinese.

① Transcript (left, scrollable)

Holds only questions, model answers and call activity: tool lines, slash-command traces (executed /xxx commands are written into the transcript so scrolling up shows what you ran), 📦 compaction, approval and rollback audit. Per-turn usage rows are no longer printed into the transcript — the token ledger lives in /stats and the resident gauge at the bottom-right of the input line (context usage, model, turns). markdown-lite highlighting, code-block coloring, automatic CJK wrapping. Thinking is grouped in blocks, shown live while streaming, and strictly folded into a single ▸ thinking · N lines line the moment the next non-thinking content arrives (replayed history folds the same way — it never auto-expands); ctrl+t expands/collapses all. Scrolling away from the bottom stops following; returning resumes.

② Input line (bottom)

Single-line input with follow-scroll. enter sends; input starting with / runs local commands and pops the candidate layer (↑↓ pick, enter runs the highlighted one, tab completes, esc closes); a uniquely matching prefix executes directly (/st → /stats). @path attaches workspace images to the message, alt+v saves a clipboard screenshot under .lyon/paste/ and fills in the @path, ↑/↓ recalls input history while idle. Typing while busy is not lost: keep typing while a prompt runs and enter queues the message; it sends automatically the moment the current answer ends (status line shows queued (1)). At the right end of the input line sits the resident usage gauge: context bar, model name, turns; on narrow terminals (input area under 40 cells) it yields the seat entirely rather than squeeze your typing.

③ Temporary output strip (below the transcript, ── output ──)

Command explanations and query results (/help /stats /model /sessions etc.) render here — up to 10 lines, then truncated; a new prompt, esc or the next command clears it — only the latest answer is ever shown, so the chat area never floods with query output.

④ Step audit panel (right)

One row per tool execution: index, name, duration, status; running rows spin, failures turn red; alt+↑/↓ walks steps, alt+enter expands the full action, alt+←/→ resizes (28–72 columns) — these keys also accept alt+shift+… variants (IDEs like Trae often swallow the plain alt keys). The panel bottom carries a resident key-legend row so you never have to memorize anything to start. When the iteration budget runs out, skipped steps are honestly marked over budget rather than disguised as failures. The panel persists with the session: the step list (with durations) is written into the snapshot on save, and returns unchanged after /resume or -c — rows that were mid-run are honestly closed as interrupted.

⑤ Evolution panel (alt+e / /evolve)

A side popup sharing the steps panel's geometry, laying the runtime state of the evolution mechanism open: one row per task class — seat holder, exam clock (0/10 rounds), mean of the recent 50 scorecards; a yellow EXAM flag means an exam is due, and (vacant) means the seat is empty. On a fresh ledger it shows getting-started hints (how to file the first scorecard, how to run an exam manually); width adjusts with alt+←/→, sharing the column with the steps panel.

Approval overlay: interactive chat pops y/n on the status line by default (off with -approve=false). y approves once · a approves that tool for the whole session (so a long task isn't interrupted ten times by the same question) · n denies (timeout/closed window always denies, fail closed; denials are not persisted).

4 ·Evolution mechanics

This is what sets lyon apart from a "one-off chat tool": tasks leave evidence, evidence becomes scores, scores decide who works, exams hold the line on capability, routing sends tasks to whoever is best at them, and gates & freezes turn the reliable parts into mechanical procedures. Four code layers: pkg/eval pkg/routing pkg/models pkg/flow. Design document: docs/design/agent-evolution.md.

  1. Production scoring → on-duty leaderboardEvery real run becomes a scorecard.
  2. Closed-book exams → eliminationTest every 10 rounds; two consecutive fails and you're out.
  3. Task classification → recommended routingHand the next task to the agent with the best evidence.
  4. Knowledge coverage gateBefore going open-book, prove you've learned it.
  5. Workflow freezing → mechanical executionReliable parts freeze into data; the LLM only fills in the blanks.

4.1 · Production scoring & the on-duty leaderboard

eval.ScoreWith scores on four dimensions: Correctness / Efficiency / Cost / Compliance weighted into Total, and DefaultThresholds requires all four to pass — everyone on duty is qualified. The leaderboard lives at $LYON_HOME/leaderboard.json, kept per task class (coding / fix / review / research / writing / design / data / general); each agent keeps its latest 50 scorecards, and every new card re-elects on-duty (freshest evidence that passes wins). Ordinary prompts auto-enter the leaderboard when finished: with no ground truth a blind judge scores them (one cheap call returns a 0–1 correctness; the TUI judges in the background, lyon run books it at the end, LYON_SCORE=off disables), and a failed judgment is not recorded — better no card than a wrong one. lyon run -flow results enter with source=flow, correctness taken from the node pass rate.

4.2 · Closed-book exams (every 10 rounds)

Handwritten bank of 4 questions for each of 8 task classes, frozen into the binary — never generated from the production tasks being examined, written to $LYON_HOME/exams/<class>.json on first use, inspectable and editable. Closed book = no tools, no file reads, only the knowledge in the weights; a question scores when the expected string matches or over half the keywords hit, DefaultExamPass = 0.75 (3 of 4). Clock: every 10 successful prompts books a round; when due and the seat is occupied an exam auto-runs; two consecutive fails → dismissed, seat vacant, the next production scorecard re-elects. Exams run async in the steps panel without interrupting your work; failures auto-summarize their causes.

4.3 · Task classification & recommended routing

routing.Classify scores bilingual keywords to class a task (ties keep the earlier class: fix → review → research → design → coding → writing → data → general); Openness(text) rates the task 0–5. The recommendation table $LYON_HOME/routing.json records the mean run score per (class, agent) with confidence mean × samples / (samples + 3) — more samples, more confidence; newcomers earn their seat with real scores. The pkg/models registry annotates all 32 models with five 0–5 profiles: Reasoning / LongHaul / Openness / Speed / Thrift. /route <text> compares the task's openness against the model profile and suggests a swap when the task exceeds it, plus workflow match suggestions.

4.4 · Knowledge coverage gate

Before working open-book, run a two-stage closed-book quiz: GenSystem generates a checkable Q/A list from the task → BookSystem blind-answers → scored against it; below CoverageThreshold = 0.6 counts as a gap, and the gap rows (question → expected answer) are spliced into the task body for targeted injection — in flows they enter every node's prompt through {{input}}. A gate error only logs gate skipped — never blocks. Entry points: lyon run -coverage (prints the score), lyon run -flow gates by default (LYON_FLOW_GATE=off disables), /flow save forces the gate and brands the gaps into the nodes.

4.5 · Workflow freezing & mechanical execution

Control flow is data, not prompt text. Workflow{slug, title, trigger, nodes} nodes carry explicit exit criteria (always / command / exit code / contains marker / narrow judge) and failure policies (retry default — bounded retries ≤3 after diagnostic feedback / abort / continue / goto, with a tick budget killing infinite loops). The state machine picks nodes, judges exits, bounds retries — the LLM only fills in the node's {{input}}; it does not decide control flow, so "decide-one-step-at-a-time" jitter disappears. Four built-ins ship frozen with the binary: feature-dev bugfix code-review release; user files $LYON_HOME/workflows/*.json override built-ins by slug.

Freeze entry /flow save <slug>: serializes this session's prompt groups into nodes, behind two gates — passing the closed-book exam for that task class + the coverage gate (gaps branded in) — before writing to disk. Execution entry lyon run -flow <slug> "task": gate → node loop (collect model output, run command criteria, narrow judge, feed diagnostics back) → results scored into the leaderboard + recommendation table → exit code 1 unless all pass. Failed prompts asynchronously run SummarizeFailure, producing checkable conditions + a patch — shown in the panel, recorded in audit.

6 ·FAQ

With an iteration budget set, why does it stop after a few dozen API calls — do I have to press enter to continue?

That's the iteration budget protecting you: with -max-iter or LYON_MAX_ITER set (positive integer), a single prompt issues at most that many API calls (MaxIterations — runaway protection, token-burn protection). By default there is no cap (MaxIterations=0): the ReAct loop runs until the model finishes on its own, or you interrupt with esc.

At the cap the transcript prints a yellow ⚡ budget reached — 50 API calls · pending tools skipped, enter to continue plus a system notification; skipped steps are honestly marked over budget in the right panel instead of being disguised as failures.

Press enter and send any message to continue from the breakpoint — history is already repaired (dangling tool_use calls get synthetic tool_results), nothing breaks. If the cap is too tight, raise it (-max-iter 100 / LYON_MAX_ITER=100) or don't set it at all.

Do the steps panel and usage stats survive /resume?

Yes. The steps panel (with per-step durations) is stored in the session snapshot and returns unchanged after resume — rows that were mid-run are honestly closed as interrupted; usage rounds are carried over with the snapshot, so /stats and the bottom-right gauge pick up where the last session left off. Snapshots saved by older versions have no step data and start counting fresh like a new session (compatible degradation, no errors). Also /new archives the current conversation and clears the panel — a new session starts clean.

Can exams or gates wedge my flow without me noticing?

No — the design principle is never block: a coverage-gate error only logs gate skipped; lyon run -exam warns on a failed exam and runs anyway; closed-book exams run async in the steps panel without interrupting the current prompt. Set LYON_EXAM=off if you don't want automatic exams at all.

Where is the data stored? Does anything go to the cloud?

All local in $LYON_HOME (default ~/.lyon): session archives, leaderboard, exam banks, routing recommendation table, workflows. No telemetry. Memory only syncs when you explicitly configure LYON_SYNC_URL/TOKEN.

How do I connect an OpenAI-compatible endpoint?

Two equivalent ways: point ANTHROPIC_BASE_URL at a compatible gateway (the protocol is parsed as Anthropic Messages), or use -openai-base https://host/v1 / LYON_OPENAI_BASE to go through the built-in OpenAI protocol translation layer. The key is reused as-is from the official one. You can also run the local lyond gateway as a reverse proxy.

Why can I keep chatting after an interrupt (esc / ctrl+c)?

An interrupt triggers history repair: a synthetic tool_result is queued for every dangling tool_use so the next request is valid. It is also the wind-down mechanism when the iteration budget tops out — so "stopped" never means "broken"; type anything and continue.

The context got compacted — where did the earlier content go?

When one turn's usage passes 0.7×200k (-compact-threshold) client-side compaction triggers: history is rendered as role-labeled text, one separate summarize request runs, and a single summary message replaces the history wholesale. The transcript shows 📦 compaction, /stats shows the matching stop=compaction turn; a checkpoint exists before the compaction so /rollback can take you back.
