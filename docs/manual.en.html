1 ·Quick start

One command builds the daemon, one starts the frontend — open the browser and you are in the workbench.

Build

# repository root (Go ≥ 1.25 required)
go build -o bin/lyond  ./cmd/lyond    # daemon: sessions / tools / approvals / gateway

# frontend dev server (hot reload; production build: npm run build)
$ cd web && npm install && npm run dev   # → http://localhost:5183

Credentials (pick one)

# A · Anthropic official endpoint
$ export ANTHROPIC_AUTH_TOKEN=sk-ant-...

# B · OpenAI-compatible endpoint (the same key works, keep the /v1)
$ export ANTHROPIC_BASE_URL=https://token-plan-cn.xiaomimimo.com/v1
$ export ANTHROPIC_AUTH_TOKEN=<your-key>

Launch

$ ./bin/lyond -addr 127.0.0.1:8080 -workspace .
# Open http://localhost:5183 in a browser — the frontend dev server
# proxies same-origin to 8080, so the bearer token rides along.
Storage root: all state (session drafts, leaderboard, exams, workflows, memory) lives in $LYON_HOME, default ~/.lyon. Change it before launch to isolate — tests, containers and CI rely on it to stay off the real home.

2 ·UI tour

Four areas: the session sidebar (left), the chat area (center), tiled panes (freely split around the right), and the footer (resident status). Pane layout persists per session and restores when you switch back.

① Session sidebar

+ new session at the top opens the workspace chooser (styled like the VS Code welcome screen: current directory / browse a folder / clone from git / a Recent list) — every session picks its own workspace and tools, files, memory and the repo map all follow that directory. Sessions are grouped by workspace: clicking a group header folds/unfolds every session under it, git repositories carry a git badge; rows show the mode, running / queued badges and the last-active time. Delete takes two clicks (× → 确认?/confirm, self-heals after 3s). The saved section at the bottom holds historical snapshots — one click restores one as a continuable session.

② Chat area

A streaming transcript: questions, model answers, tool cards and approval cards. Full markdown rendering — hovering a code block reveals a copy button, tool output is color-coded by exit code and keywords; thinking shows live while streaming, then folds strictly into one line, with ctrl+o toggling every folded block at once. Each turn ends with a produced-files card (files this run wrote/changed, diff-based so parallel sessions' writes never leak in). Typing while busy is not lost: enter queues the message, injected at the next tool-execution gap; the sidebar row shows the queued count.

③ Tiled panes

Panes split horizontally and vertically, the same kind can open twice, and the layout persists with the session:

The top bar toggles the dashboard view (task-execution statistics). The mind map sits beside chat: ctrl+wheel zooms, middle-drag pans; picking mindmap mode brings the map forward, and editing the map feeds back as a follow-up that advances the conversation.

④ Footer

Left: the mode chip — click to open the picker, shift+tab cycles default → plan → bypass (mindmap comes from the picker or /mindmap); center: the resident hint / for commands · shift+tab mode · ↑ history and the model button (click through to the settings pane; 👁 means the model takes image input); bottom-right: the context gauge — an HP bar colored by load (green < 20% ≤ amber ≤ 70% < soft red) with the spend next to it.

Approval cards: shell / file writes ask as a card that states why it is asking (matches …) and highlights the matched span of the input; three buttons — approve(y) · deny(n) · always(a) (a = allow that tool for the whole session). In plan mode the interception card switches to policy vocabulary: allow just this file f / switch to default d / switch to bypass b / deny n. Keys y n a answer directly (they never touch the input box).

4 ·Evolution mechanics

This is what sets lyon apart from a "one-off chat tool": runs leave evidence, evidence becomes scores, scores decide who works, exams hold the line on capability, routing records who is best, and gates & freezes turn the reliable parts into mechanical procedures. The evolution loop lives in pkg/evolve and is driven by lyond's prompt_end hook — web sessions and every other entry point run the same loop. Design document: docs/design/agent-evolution.md.

  1. Production scoring → on-duty leaderboardEvery real run becomes a scorecard.
  2. Closed-book exams → eliminationTest every 10 rounds; two consecutive fails and you're out.
  3. Task classification → recommended routingClass tasks; evidence flows into the recommendation table.
  4. Knowledge coverage gateBefore going open-book, prove you've learned it.
  5. Workflow freezing → mechanical executionReliable parts freeze into data; the LLM only fills in the blanks.

4.1 · Production scoring & the on-duty leaderboard

eval.ScoreWith scores on four dimensions: Correctness / Efficiency / Cost / Compliance weighted into Total, and DefaultThresholds requires all four to pass — everyone on duty is qualified. The leaderboard lives at $LYON_HOME/leaderboard.json, kept per task class (coding / fix / review / research / writing / design / data / general); each agent keeps its latest 50 scorecards, and every new card re-elects on-duty (freshest evidence that passes wins). Ordinary prompts auto-enter the leaderboard when finished: with no ground truth a blind judge scores them (one cheap call returns a 0–1 correctness, booked asynchronously after the prompt ends, LYON_SCORE=off disables), and a failed judgment is not recorded — better no card than a wrong one.

4.2 · Closed-book exams (every 10 rounds)

Handwritten bank of 4 questions for each of 8 task classes, frozen into the binary — never generated from the production tasks being examined, written to $LYON_HOME/exams/<class>.json on first use, inspectable and editable. Closed book = no tools, no file reads, only the knowledge in the weights; a question scores when the expected string matches or over half the keywords hit, DefaultExamPass = 0.75 (3 of 4). Clock: every 10 successful prompts books a round; when due and the seat is occupied an exam auto-runs; two consecutive fails → dismissed, seat vacant, the next production scorecard re-elects. Exams run async and never interrupt the current prompt; the clock and the bank are readable in the evolve pane, and LYON_EXAM=off opts out (rounds still count).

4.3 · Task classification & recommended routing

routing.Classify scores bilingual keywords to class a task (ties keep the earlier class: fix → review → research → design → coding → writing → data → general); Openness(text) rates the task 0–5. The recommendation table $LYON_HOME/routing.json records the mean run score per (class, agent) with confidence mean × samples / (samples + 3) — more samples, more confidence; newcomers earn their seat with real scores. The pkg/models registry annotates all 32 models with five 0–5 profiles: Reasoning / LongHaul / Openness / Speed / Thrift. Classes, leaderboard and the recommendation table are directly readable in the evolve pane's /route section.

4.4 · Knowledge coverage gate

Before working open-book, run a two-stage closed-book quiz: GenSystem generates a checkable Q/A list from the task → BookSystem blind-answers → scored against it; below CoverageThreshold = 0.6 counts as a gap, and the gap rows (question → expected answer) are spliced into the task body for targeted injection. The implementation lives in pkg/eval/coverage.go, with the runner adapters in pkg/flow/glue.go (NewGate / NewDiagnose). The design principle is never block: a gate error only logs gate skipped and never holds a task up.

4.5 · Workflow freezing & mechanical execution

Control flow is data, not prompt text. Workflow{slug, title, trigger, nodes} nodes carry explicit exit criteria (always / command / exit code / contains marker / narrow judge) and failure policies (retry default — bounded retries ≤3 after diagnostic feedback / abort / continue / goto, with a tick budget killing infinite loops). The state machine picks nodes, judges exits, bounds retries — the LLM only fills in the node's {{input}}; it does not decide control flow, so "decide-one-step-at-a-time" jitter disappears. Four built-ins ship frozen with the binary: feature-dev bugfix code-review release; user files $LYON_HOME/workflows/*.json override built-ins by slug.

The in-session entry point is the agent's flow tool (three actions: list shows the frozen slugs · run executes a fixed step sequence with named args · freeze saves a just-proven sequence under a slug) — the model can replace re-deriving an entire command sequence with a single call. Frozen flows, the freeze clock and execution traces persist under $LYON_HOME and are readable in the evolve pane's /flow section.

Historical live-run validation (2026-10-12 19:12 → 10-13 06:34, 11 h 21 m): an overnight driver finished 224 rounds, all exited 0 (zero failures), ~3 min/round; 20 closed-book exams 18 PASS / 2 FAIL — a sitting model that lost two in a row was demoted and the seat re-elected on production evidence (the expelled agent never gets the seat back for free); 206 blind-judge scores filed in the 0.80–1.00 range, so grades genuinely discriminate; the bugfix flow froze after 18 consecutive greens, and the final routing table showed fix at 100 samples / confidence 0.96. The original driver scripts shipped with the legacy demo and are gone; the artifacts remain inspectable under $LYON_HOME.

6 ·FAQ

With an iteration budget set, why does it stop after a few dozen API calls?

That's the iteration budget protecting you: with -max-iter or LYON_MAX_ITER set (positive integer), a single prompt issues at most that many API calls (runaway protection, token-burn protection). By default there is no cap: the ReAct loop runs until the model finishes on its own, or you hit stop.

At the cap the session shows a budget reached notice; skipped steps are honestly marked over budget in the steps pane instead of being disguised as failures.

Send any message to continue from the breakpoint — history is already repaired (dangling tool_use calls get synthetic tool_results), nothing breaks. If the cap is too tight, raise it (LYON_MAX_ITER=100) or don't set it at all.

Do the transcript and steps survive switching sessions or refreshing the page?

Yes. They ride the server-side event stream: opening a session first fetches the history batch (GetHistory), then WatchEvents continues the live tail — refresh or switch away and back, it is the same stream. Usage rounds keep counting with the session, so the footer gauge picks up where it left off. The saved snapshots in the sidebar are cross-process archives: restore one and it becomes a continuable session.

Can exams or gates wedge my flow without me noticing?

No — the design principle is never block: a coverage-gate error only logs gate skipped; closed-book exams run async and never interrupt the current prompt; a failed exam only warns and still records. Set LYON_EXAM=off if you don't want automatic exams (add LYON_SCORE=off to also skip blind scoring).

Where is the data stored? Does anything go to the cloud?

All local in $LYON_HOME (default ~/.lyon): session drafts and snapshots, leaderboard, exam banks, routing recommendation table, workflows, memory. No telemetry. Memory only syncs when you explicitly configure LYON_SYNC_URL/TOKEN.

How do I connect an OpenAI-compatible endpoint?

Two equivalent ways: point ANTHROPIC_BASE_URL at a compatible gateway (the protocol is parsed as Anthropic Messages), or use -openai-base https://host/v1 / LYON_OPENAI_BASE to go through the built-in OpenAI protocol translation layer. The key is reused as-is from the official one; you can also point ANTHROPIC_BASE_URL at a local recording/translation proxy.

Why can I keep chatting after an interrupt?

An interrupt triggers history repair: a synthetic tool_result is queued for every dangling tool_use so the next request is valid. It is also the wind-down mechanism when the iteration budget tops out — so "stopped" never means "broken"; type anything and continue.

The context got compacted — where did the earlier content go?

When one turn's usage passes 0.7×200k (-compact-threshold) client-side compaction triggers: history is rendered as role-labeled text, one separate summarize request runs, and a single summary message replaces the history wholesale. The transcript shows 📦 compaction; a checkpoint exists before the compaction so /rollback can take you back.
