# 分析与建议备忘（2026-10-15 lyon 会话 dump）

> 本文件是当日多轮探讨的完整结论存档：设计哲学、记忆机制评估、agent 差异、
> 同行借鉴、速度/并发分析。可执行任务已拆到 `EVOLUTION-GAPS.md`（修断点）
> 与 `ROADMAP.md`（产品路线），本文是它们背后的分析依据，不重复任务细节。

## 一、设计哲学（一句话 + 四条）

**一句话：流程交给确定性机制，模型只填内容——一切状态都是可重放的本地文件。**

1. **机械的归机制，聪明的归模型**：选拔、评分、淘汰、路由、workflow 状态机、
   审批、审计全是确定性代码；模型只负责填空、判断、写内容。「下一步做什么」
   永远不由 LLM 拍脑袋决定。
2. **一切皆文件**：记忆是一事实一文件 markdown、榜单/路由/考试/流程固化全是
   JSON（tmp+rename 原子写）、审计是 jsonl。没有数据库、没有服务、没有云端
   依赖——`$LYON_HOME` 删了就是失忆，拷走就是搬家，任何决策可离线重放。
3. **证据治国**：上岗靠考分，留任靠生产分，连挂 2 次撤职，路由换手靠
   样本数×置信度，流程固化要连绿。没有「感觉差不多了」，只有记分卡。
4. **增量、可杀**：每个机制都是外挂一层（hooks 事件流、文件账本），关掉任何
   开关（`LYON_SCORE=off` 等）系统照常是普通 agent；best-effort——记忆坏了
   给空层，路由没证据就自己上，重试从不发完全相同的请求。

弱点也在这套哲学里：**回流不闭环就只剩记账**（EVOLUTION-GAPS 五断点的共同
根因）——机制都太被动，记了不喂回去，进化就发生在账本上而不是行为上。

## 二、记忆机制评估与同行对比

### 现状（`pkg/memory` 1300 行）

三层作用域（team/personal/project）+ 一事实一文件 + **BM25 倒排索引**
（CJK 二元组分词、字段加权 name×3/tags×2.5/desc×2/body×1、微秒级、零外部
依赖）+ 热层（`hot: true` → 4KB 预算渲染进 system prompt）+ 晋升通道
（hits ≥2 + distill 复述确认）+ 云同步（dumb JSON push/pull，newer-wins）。

### 同行对比表

| | lyon | Claude Code | Letta (MemGPT) | mem0 | ChatGPT memory |
| --- | --- | --- | --- | --- | --- |
| 分层 | 热（常驻）/冷（检索） | CLAUDE.md 全热，无检索层 | core（热）/archival（检索）/recall（会话） | 向量库无分层 | 全注入无分层 |
| 检索 | BM25+二元组，本地毫秒 | 无 | 向量 | 向量+图 | 无 |
| 语义召回 | ❌（改述搜不到） | — | ✅ | ✅ | — |
| 自我编辑 | 写盘可以，当前会话不刷新 | 会话中可改 CLAUDE.md | ✅ core 块会话内自编辑 | 服务端 | ✅ |
| 会话/情景记忆 | snapshot 另存，不可从记忆检索 | — | ✅ recall | ✅ | — |
| 蒸馏 | 自动（退出）+晋升 | 半自动 | agent 主动 | LLM 抽取 | 自动 |
| 本地可控 | ✅ 纯文件 | ✅ | 部分 | ❌ | ❌ |

**结论**：架构优于 Claude Code（它没有冷层），与 Letta 同思路、更轻更本地。
BM25 不上 embedding 是务实取舍（无 embedding 服务时的最优解），勿引入。

### 三个真实缺口（已拆为 EVOLUTION-GAPS 任务 D）

1. **热层是会话创建时的快照**（session.go:185）——会话中途写入的记忆当前
   会话永远看不到；与 Letta 的核心差距（它 core 块会话内自编辑）。
2. **写入端饿着**：真实 store 里 personal 只有 1 条事实——库是空的，再好的
   检索也没东西返回。
3. **只有陈述性事实，无情景记忆**：会话快照与记忆库是两个孤岛；
   hits 只增不减、无衰减淘汰（几百条前无所谓）。
   另：Search 每次命中重写 k 个文件持久化计数器（D2）。

## 三、agent 间差异：设计 vs 实现（断点 5 原文依据）

- **设计**（agent-evolution.md §1.1）：候选只允许在 {模型, prompt_ref,
  工具白名单, params} 四维上不同，带 parent+gen，patch 追加重试、
  每代必须比上代分高否则淘汰。
- **实现**（`pkg/eval/candidates.go`）：真实生效的差异 = **模型 + effort 两维**；
  prompt_ref/tools 白名单字段不存在；`Gen`/`Parent` 是死字段（全仓无人写入，
  依赖任务 A 的 patch 回流先接上）。
- `/contest` 实际是「同一提示词、同一工具下的模型选型竞赛」；
  `self`（运行中主模型）永远在场，单模型时候选场 = self 一人。

## 五、速度与并发分析（「并发倾向」需求的完整论证）

### 并发现状（已就位的基建）

- 工具级：一轮多个 tool_use 时只读工具并发、写类拿 serialMu（tool.go:224）；
- 子代理：run_subagents 扇出 2–6 子任务全并发（dispatch.go:34 明文写着
  「并发倾向 requirement — Go-style maximal concurrency is the product stance」）；
- 引擎级：MaxConcurrentTurns 限流；lyond 多会话并发。

### 缺口 = 「在架子上，不在习惯里」

1. system prompt 关于并发只有一句话（Batch independent reads）；
2. todo 计划是串行列表，从不表达独立组；
3. 并发度无人度量（stats 只有 subagents 总数）。
→ 已拆为 ROADMAP 1.6（F1 prompt 习惯回路 / F2 计划感知 / F3 度量闭环）。

### 「AI 规划并发」为什么是对的分工

任务间有无**数据依赖**是语义判断，静态规则判不准，只有模型能判。正确架构 =
引擎提供原语和安全边界，模型负责规划——正是现状。缺的只是习惯与度量回路。

### 性能真相（对外叙事纪律）

- **Go 层高效**：引擎 overhead p95 门限 25ms（实测 ~16ms），记忆微秒级；
- **端到端是模型/网关绑定**：demo ~3 分钟/轮里本地开销只有几十毫秒，
  其余全是网关延迟（实测抖动 2s–10s）+ 模型思考；
- **解药不是优化 lyon**：①减少轮次（repo-map、workflow 机械执行）
  ②重叠等待（fan-out）③prefix cache（-prewarm 已有）；
- **叙事纪律**：对外不吹「快」，吹「等待被重叠、轮次被省掉」——可验证承诺；
- 并发提的是墙钟时间不是吞吐成本：K 个子代理 = K 份 token，
  opus 档要掂量，F3 度量闭环让这笔账可见。

### 能比别的 agent 快吗？

三条赛道：

| 赛道 | Claude Code | lyon 机会 |
| --- | --- | --- |
| 宽度（并发） | 已很强 | 打平或小胜 |
| 轮次效率 | 顶级工程打磨 | 难胜，repo-map 可追近 |
| **模型选择** | 单模型 | **唯一结构性胜机**：routing 把短平快任务路由到 flash 档 |

- 简单重复类任务：快模型 + workflow 省决策轮，**有机会明显快**；
- 复杂链式任务：难，轮次效率拼内功；
- 宽度型：平手。
- **衍生素材**：同一任务集实测「lyon 路由版 vs Claude Code 单模型」墙钟对比
  ——竞技榜第一期爆款选题：「不是我快，是我知道该让谁干」。
